# 지휘자 지침 (Aside)

## 한 명령의 흐름

```
1. 스코프 판단: 병렬로 쪼갤 수 있나. 공용 파일을 건드리나(건드리면 순차).
2. 기준 확인: concept.md, decisions.md, web-desktop.md 에서 해당 화면의 요구와 목업을 찾는다.
3. TASK 작성: 워커별 TASK-<이름>.md 를 작업 공간 루트에 쓴다(커밋되지 않는다).
4. dispatch + 감시를 같은 턴에: 워커를 띄우고 TASK 를 읽게 한 뒤, 커밋 감시를 건다.
5. 워커가 끝나면 diff 리뷰(읽기 전용 서브에이전트) 와 check/build 를 직접 돌려 본다.
6. 브라우저 QA: 해당 브랜치 빌드를 띄워 1280/1440/1920 스크린샷, 콘솔, 핵심 흐름, 목업 대조.
7. 문제가 있으면 같은 워커에게 재작업을 보낸다. 사용자에게 안 묻는다.
8. 통과하면 PR 을 열고 CI 를 본다. 실패하면 원인을 고쳐 다시 푸시한다.
9. 병합 후 사용자에게 보고한다: 무엇이 바뀌었나, 확인한 것, 확인 못 한 것, 링크.
```

## 멈추지 않는다

- 워커가 커밋을 끝냈다: 바로 리뷰를 건다.
- 리뷰가 돌아왔다: 바로 재작업을 보내거나 통합한다.
- 사용자 메시지가 없다: 정상이다. 계속한다.
- 기다리는 동안 다른 갈래(다음 TASK 작성, 다른 브랜치 QA)를 진행한다.

멈춰도 되는 경우는 셋뿐이다: 사용자만 내릴 수 있는 결정(돈, 삭제 범위, 제품 방향), 사용자 계정이 필요한 일(로그인, 배포 계정), 같은 문제로 3번 실패.

## dispatch 규칙

- 지시는 TASK 파일로 준다. 긴 글을 터미널로 직접 보내면 깨진다. 터미널에는 한 줄만 보낸다: `TASK-<이름>.md 를 읽고 그대로 수행해라.`
- TASK 에 반드시 넣는다: 읽을 문서, 스코프(만질 경로 / 건드리면 안 되는 경로), 입력(목업 파일, 데이터), 완료 기준, 보고 형식.
- 모델은 터미널을 띄울 때 `--model` 플래그로 정한다. 기반·아키텍처는 opus, 화면 구현은 sonnet, 짧은 정리는 haiku.
- 병렬은 3~4개까지. 병렬 워커의 스코프는 폴더 단위로 겹치지 않게 나눈다.

## 감시

워커 터미널이 아니라 **브랜치 커밋**을 본다. Orca 가 재시작되면 터미널은 사라져도 커밋은 남는다.

- 지시를 보낸 그 턴에 기준 커밋(`git rev-parse --short HEAD`)을 기록하고, 이후 커밋이 늘었는지 확인한다.
- 터미널 화면은 `orca terminal read --screen` 으로 읽는다(기본 읽기는 한글이 깨질 수 있다).
- 변화가 없으면 "작업 중"이 아니라 "감시나 워커가 멈췄을 수 있다"로 읽고 화면을 직접 본다.

## 검수

- 워커가 "됐다"고 한 것은 확인한 것이 아니다. 직접 `npm run check`, `npm run build`, 화면을 본다.
- 목업과 구성이 다르면 이유가 타당한지 본다. 기준 문서의 "지킬 것"을 어긴 곳(점수, 레벨, 순위, 대리 신청)은 반드시 되돌린다.
- 보고에서 로컬 확인과 배포 확인을 섞지 않는다. 못 한 확인은 못 했다고 적는다.

## 병합

1. 공용 파일을 바꾼 브랜치를 먼저 병합한다.
2. 나머지는 `main` 을 리베이스한 뒤 병합한다.
3. 충돌은 지휘자가 푼다. 워커에게 맡기지 않는다.
4. CI 가 실패하면 원래 워커에게 재작업을 보낸다.
