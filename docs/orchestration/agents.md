# 워커 지침

각 워커는 새 컨텍스트로 뜬다. 이 문서와 TASK 파일이 전부라고 생각하고 읽는다. 사용자와 직접 대화하지 않고, 결과는 지휘자에게만 보고한다.

## 공통

- 시작 전에 읽는다: `CLAUDE.md`, `docs/product/concept.md`, `docs/design/web-desktop.md`, TASK 파일.
- 자기 작업 공간(worktree)과 TASK 의 스코프 밖은 건드리지 않는다. 스코프 밖 수정이 필요하면 직접 하지 말고 보고한다.
- 끝났다고 말하기 전에 `npm run check`, `npm run build` 를 돌려 출력을 확인하고, UI 는 스크린샷으로 눈으로 본다.
- 막히면 막힌 이유와 필요한 것을 보고한다. 사용자에게 묻지 않는다.
- 작은 단위로 자주 커밋하고, 끝나면 푸시한다(`git push -u origin HEAD`). PR 은 지휘자가 연다.

## 기반 (foundation)

- 담당: `src/app`, `src/components`, `src/styles`, `src/domain`, 공용 타입, 라우팅, 전역 상태, CI.
- 화면 워커가 병렬로 일할 수 있게 **경계를 먼저 만든다**: 화면 폴더 stub, 공용 컴포넌트, 상태 접근 방법.
- 기존 로직(추천 규칙, 발견 생성)을 화면에서 분리하고 테스트를 붙인다.

## 화면 (screen)

- 담당: TASK 에 적힌 `src/screens/<이름>/**` 와 `src/data/<이름>.ts` 만.
- 공용 컴포넌트와 토큰을 쓴다. 필요한 변형이 없으면 화면 폴더 안에서 감싸서 쓰고, 공용 개선이 필요하다고 보고한다.
- 목업은 참고용이다. 기준 문서와 다르면 기준 문서를 따른다.
- 예시 데이터는 지어내도 되지만 실제 사람 이름, 학번, 연락처는 쓰지 않는다.

## 보고 형식 (한국어 5줄 내외)

```
한 것: (화면과 파일 경로)
check/build: (통과 또는 실패, 실패면 이유)
본 것: (확인한 폭, 스크린샷 수, 콘솔 에러 수, 통과시킨 흐름)
남은 것 / 목업과 다른 점: (없음 또는 무엇을 왜)
공용 파일에 필요한 변경: (없음 또는 무엇)
```

## 리뷰어 (읽기 전용)

코드를 고치지 않는다. 문제만 보고한다. `npm run check` 는 이미 통과했다고 가정하고 도구가 못 잡는 것만 본다.

1. 기준 문서의 "지킬 것"을 어겼나 (점수·레벨·순위, 대리 신청, 공개 범위).
2. 이미 있는 컴포넌트·토큰·헬퍼를 다시 만들었나. 토큰 밖 값을 직접 박았나.
3. 로딩·빈·오류 상태와 키보드 접근이 있나.
4. 스코프 밖 파일을 건드렸나.
5. 테스트가 실제 로직을 검증하나.

형식: `파일:줄 — 문제, 바꿀 방향` 한 줄씩. 심각한 것부터. 없으면 없다고 쓴다.
