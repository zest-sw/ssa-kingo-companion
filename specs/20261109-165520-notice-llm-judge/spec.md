# Feature Specification: 공지 판정에 로컬 LLM 더하기

**Feature Branch**: `feat/cse-notices` (스펙 1과 같은 브랜치에서 로컬로 이어 작업)

**Created**: 2026-11-09

**Status**: Done 2026-11-10 (최종 평가 7개 중 6개 통과, SC-006 주최 87.5% 미달을 알려진 한계로 마무리: research R13)

**Input**: User description: "공지 ETL에 로컬 LLM(Ollama) 판정 단계를 더한다. 스펙 1 다음 기능이고, 2026-11-09 브레인스토밍에서 사용자가 승인한 설계(판정 범위, 실패 처리, 평가 방법, 파일과 검사)를 따른다."

> **배경**: 스펙 1([../20261107-193624-cse-notice-opportunities/spec.md](../20261107-193624-cse-notice-opportunities/spec.md))은 제목 단어 규칙으로 공지를 기회로 나눈다. 처음 보는 2차 평가용 100건에서 SC-001 기회 여부 93.3%, SC-003 종류 88.6%, SC-006 주최 88.6%, SC-007 확인 필요 11.0%로 미달했고, 마감(정확 98.0%, 채움 89.1%)은 기준을 넘었다(스펙 1 research R18). 미달 넷은 기간마다 새 낱말과 경계 사례가 나오는 제목 단어 규칙의 한계다. 기준 문서(`docs/product/concept.md`)는 글 분류를 키워드 규칙으로 먼저 나누고 규칙에 안 걸리는 글만 LLM으로 보내며, 일정·마감 같은 사실은 로직이 뽑은 값만 쓴다고 정했다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 규칙이 못 정하거나 헷갈리는 글을 로컬 LLM이 판정한다 (Priority: P1)

개발자가 ETL을 한 번 실행하면, 고른 방식에 해당하는 글을 이 컴퓨터에서 도는 LLM이 읽고 기회 여부와 종류를 정한다. 주최와 마감은 지금처럼 규칙이 정한다(주최는 2026-11-10 결정, FR-001). 결과 파일과 요약에서 LLM이 정한 글을 알아볼 수 있다.

**Why this priority**: 스펙 1에서 미달한 넷(기회 여부, 종류, 주최, 확인 필요)을 고치는 것이 이 기능의 목적이다. 이것 없이는 나머지가 의미 없다.

**Independent Test**: LLM 서버를 켜고 90일치를 실행하면, 확인 필요였던 글이 기회나 기회 아님으로 정해지고 분류 근거가 'LLM: <모델 이름>'으로 나온다.

**Acceptance Scenarios**:

1. **Given** 스펙 1 규칙이 '규칙에 안 걸림'으로 확인 필요에 보낸 '[SK그룹] Pre-SKALA 참여자 모집 (~10/14 09시까지)'이 있을 때, **When** 실행하면, **Then** LLM이 기회, 교육·캠프로 정하고, 분류 근거는 'LLM: <모델 이름>', 마감은 규칙이 제목에서 읽은 날(10/14)이다.
2. **Given** LLM이 어떤 글의 종류를 규칙과 다르게 특강으로 정할 때, **When** 마감을 정하면, **Then** 특강의 마감 규칙(신청 마감이 없으면 행사 날)을 다시 적용한다.
3. **Given** LLM 답에 날짜가 들어 있어도, **When** 결과를 만들면, **Then** 마감에는 규칙이 뽑은 값만 쓴다.
4. **Given** LLM 답의 종류가 11종에 없거나 답이 JSON이 아닐 때, **When** 판정하면, **Then** 그 글은 규칙 결과를 쓰고 요약의 실패 수에 들어간다.
5. **Given** 같은 글을 다시 실행할 때, **When** 모델과 지시문 판이 그대로면, **Then** LLM에 다시 묻지 않고 보관한 답을 쓴다(요약의 '보관' 수).

---

### User Story 2 - 후보 모델과 방식을 정답셋으로 비교해 고르고 한 번 잰다 (Priority: P2)

개발자가 후보 로컬 모델 2~3개, 보낼 글 두 방식, 확신 '낮음' 처리 두 가지를 개발용 정답셋으로 비교한다. 기준을 넘기는 조합 중 가장 빠른 것을 고르고, 처음 보는 평가용 100건으로 한 번만 잰다.

**Why this priority**: 로컬 모델은 크기와 한국어 능력에 따라 정확도와 속도가 크게 다르다. 재 보지 않고 고르면 스펙 1처럼 처음 보는 글에서 미달이 되풀이된다.

**Independent Test**: 조합별 SC-001~SC-007과 실행 시간 비교표, 고른 조합, 평가용 최종 성적이 research에 남는다.

**Acceptance Scenarios**:

1. **Given** 모델 하나의 답을 개발용 전체에 대해 받아 보관했을 때, **When** 조합별 지표를 계산하면, **Then** LLM에 다시 묻지 않고 보관한 답으로 계산한다.
2. **Given** 어떤 조합도 SC-001~SC-007을 모두 넘기지 못할 때, **When** 조합을 고르면, **Then** 가장 많이 넘기는 조합을 고르고 그 사실을 사용자에게 알린다.
3. **Given** 조합과 지시문을 확정했을 때, **When** 2025년 1~4월 평가용 100건을 처음 돌리면, **Then** 그 결과를 최종 성적으로 기록하고 평가용을 보고 아무것도 고치지 않는다. 기준에 못 미치면 원인을 보고하고 다음 단계는 사용자가 정한다.
4. **Given** 고른 방식이 기준 문서('규칙에 안 걸리는 글만 LLM으로')와 다를 때, **When** 조합을 확정하면, **Then** 결정 로그 초안을 사용자에게 낸다.

### User Story 3 - LLM이 없거나 실패해도 ETL은 끝까지 돈다 (Priority: P3)

LLM 서버가 꺼져 있거나, 설정한 모델이 없거나, 한 글의 판정이 실패해도 ETL은 멈추지 않는다. 그 글들은 규칙 결과로 나가고, 요약에서 무엇이 빠졌는지 안다.

**Why this priority**: 수집, 규칙, 마감은 스펙 1에서 검증됐다. LLM 때문에 결과가 멈추거나 비면 안 된다. 다른 팀원 컴퓨터에는 LLM 서버가 없을 수 있다.

**Independent Test**: LLM 서버를 끄고 실행하면 결과 파일이 써지고, 보관한 답이 있는 글은 그 답을, 새 글은 규칙 결과를 쓰고, 요약에 연결 실패 한 줄이 붙는다.

**Acceptance Scenarios**:

1. **Given** LLM 서버가 꺼져 있을 때, **When** 실행하면, **Then** 보관한 답이 있는 글은 그 답을, 나머지 K건은 규칙 결과를 쓰고, 결과 파일을 쓰며, 요약에 'LLM에 연결하지 못해 K건은 규칙만 썼어요 (<모델 이름>)'가 붙는다.
2. **Given** 한 글의 답이 120초 안에 오지 않을 때, **When** 판정하면, **Then** 그 글만 규칙 결과를 쓰고 답을 보관하지 않아 다음 실행에서 다시 묻는다.
3. **Given** 설정한 모델이 LLM 서버에 없을 때, **When** 실행하면, **Then** 1번과 같이 처리한다.

---

### Edge Cases

- LLM 답이 코드 블록(```json … ```)에 싸여 오면 벗겨서 읽는다.
- 주최가 빈 문자열이면 '없음'으로 본다. 주최가 40자를 넘으면 실패로 본다(본문 문장을 옮겨 적은 답을 막는다).
- 기회가 X인 답에 종류나 주최가 함께 오면 버린다.
- 본문 글자가 없는 글(포스터뿐)은 제목과 게시판만 보낸다.
- '확인 필요만' 방식에서는 규칙이 정한 글을 LLM에 보내지 않는다. '모든 글' 방식에서는 규칙이 기회 아님 단어로 뺀 글도 보낸다.
- 지시문 판이나 모델 이름이 바뀌면 이전 판·다른 모델의 보관 답은 쓰지 않는다.
- 연결 실패를 한 번 알면 그 실행의 남은 글은 LLM에 다시 묻지 않는다(글마다 기다리지 않는다).
- LLM이 기회로 정한 글끼리도 스펙 1의 중복 정리(같은 제목·같은 마감은 최근 글 하나)를 적용한다.

## Requirements *(mandatory)*

### Functional Requirements

**판정**

- **FR-001**: 시스템은 고른 방식에 해당하는 글을 로컬 LLM에 보내 기회 여부와 종류를 받아야 한다. 방식은 '확인 필요만'(규칙이 확인 필요로 보낸 글)과 '모든 글'(LLM이 실패한 글은 규칙 결과) 중 US2 비교로 정한다. 주최는 LLM이 정한 기회도 스펙 1 규칙(제목 대괄호) 값을 쓴다(2026-11-10 사용자 결정: LLM 주최는 개발용에서 SC-006에 못 미쳤다, research R12).
- **FR-002**: LLM에 보내는 내용은 제목, 게시판 분류, 본문 글자 앞부분(앞 60줄과 그 뒤의 날짜·신청 단어가 든 줄, 120줄과 합쳐 8,000자까지, 한 줄 300자까지)이다. 규칙 결과나 다른 글은 보내지 않는다. 본문을 받지 못한 글(스펙 1 '본문 못 받음')은 보내지 않는다.
- **FR-003**: 지시문은 스펙 1 [gold-guide.md](../20261107-193624-cse-notice-opportunities/gold-guide.md)(정답 기준, 종류 11종 뜻 표, 좁은 쪽 우선 순서, 애매한 글 기준 5가지, 주최 규칙)와 그 문서의 예시 제목으로 만든다. 판은 지시문, 답 스키마, 사용자 메시지 틀, 자르기 한도, 요청 옵션의 내용으로 저절로 정해진다. 이 중 하나라도 바뀌면 판이 바뀐다.
- **FR-004**: LLM 답은 기회(O/X), 종류(11종 이름 그대로: 채용, 특강, 해커톤, 대회·공모전, 교육·캠프, 동아리·학회, 봉사, 멘토링, 글로벌, 장학, 교과), 주최(기관 이름, 모르면 '없음'), 확신(높음/낮음)이다. 이 꼴이 아니면(JSON이 아님, 모르는 종류, 빠진 칸) 실패다. 답의 주최는 결과에 넣지 않고(FR-001), 40자를 넘으면 본문 문장으로 보고 버린다(답은 받는다, 2026-11-10 코드 리뷰 뒤 변경). 지시문을 다음에 바꿀 때 주최 칸을 뺀다.
- **FR-005**: 확신 '낮음' 답은 고른 처리(그대로 받기 / 확인 필요로 두기)를 따른다. US2 비교로 정한다.
- **FR-006**: LLM이 정한 기회의 분류 근거는 'LLM: <모델 이름>'이다. 확신이 낮아 확인 필요로 둔 글의 이유는 'LLM 확신 낮음'이다. 근거와 이유에 본문 문장을 넣지 않는다.
- **FR-007**: 마감은 LLM 답과 상관없이 규칙이 정한다. LLM이 정한 종류가 규칙과 다르면 LLM이 정한 종류로 마감 규칙을 다시 적용한다. LLM 답의 날짜는 어디에도 쓰지 않는다.
- **FR-008**: 스펙 1의 중복 정리(FR-018)는 LLM 판정까지 끝난 기회 목록에 적용한다.

**보관**

- **FR-009**: 시스템은 성공한 LLM 답을 글 번호, 모델 이름, 지시문 판마다 보관하고, 셋이 같으면 다시 묻지 않아야 한다. 실패한 답은 보관하지 않는다. 보관 위치는 저장소 기록에서 빠져 있어야 한다.
- **FR-010**: 같은 글, 같은 모델, 같은 지시문 판으로 다시 실행하면 판정과 근거가 같아야 한다.

**설정**

- **FR-011**: 모델 이름과 LLM 서버 주소는 실행 환경 설정으로 바꿀 수 있어야 한다. 설정이 없으면 기본값(US2로 고른 모델, 이 컴퓨터의 서버)을 쓴다. 모델 이름은 이 한 곳에서만 정한다(나중에 관리자 화면이 바꿀 자리).

**실패**

- **FR-012**: LLM 서버에 닿지 못하거나 설정한 모델이 없으면, 시스템은 실행을 멈추지 않고 보관한 답은 쓰고 나머지 글은 규칙 결과로 내며 결과 파일을 써야 한다. 규칙 결과로 낸 글이 K건(K>0)이면 요약에 'LLM에 연결하지 못해 K건은 규칙만 썼어요 (<모델 이름>)' 한 줄을 붙인다. K가 0이면 붙이지 않는다.
- **FR-013**: 서버에 닿았지만 글 하나의 답이 120초 안에 오지 않거나, 서버가 다른 오류로 답하거나, 답의 꼴이 틀리면 그 글만 규칙 결과를 쓴다.
- **FR-014**: LLM 요청은 한 번에 하나씩 보낸다.
- **FR-015**: 서버에 닿지 못함이나 모델 없음을 한 번 알면 그 실행에서는 서버를 다시 부르지 않는다. 보관한 답은 그 뒤에도 읽어 쓴다. 처음 실패를 알린 글을 포함해, 서버를 부르지 못해 규칙 결과로 낸 글은 모두 K에 센다.

**요약과 결과 파일**

- **FR-016**: 스펙 1 요약(FR-024) 끝에 'LLM 판정 N(보관 A · 새로 B · 실패 C)'를 붙인다. A는 보관한 답을 쓴 글, B는 이번에 새로 받은 답을 쓴 글, N은 A+B, C는 실패해서 규칙 결과를 쓴 글 수다. LLM에 보내지 않은 글은 어디에도 세지 않는다.
- **FR-017**: 결과 파일의 모양(스펙 1 contracts)은 그대로다. 분류 근거 값에 'LLM: <모델 이름>', 확인 필요 이유 값에 'LLM 확신 낮음'이 더해진다. 스펙 1 data-model의 '근거에 쓰는 말'을 함께 고친다.

**평가**

- **FR-018**: 개발용 정답셋은 501건이다(스펙 1 개발용 401건과 2차 평가용 100건). 지시문은 개발용만 보고 다듬는다.
- **FR-019**: 후보 모델은 2~3개다(이미 받아 둔 Gemma 4 E4B와 한국어에 강한 7~14B급 한두 개). 이 컴퓨터의 `gemma-4-longctx:latest`와 `hf.co/ggml-org/gemma-4-E4B-it-GGUF:latest`는 같은 가중치라 후보 하나로 센다. 모든 후보는 같은 요청 옵션(문맥 길이 포함)으로 묻는다. Claude가 새 후보를 크기·메모리·라이선스와 함께 제안하고, 사용자가 확인한 뒤에 내려받는다.
- **FR-020**: 시스템은 모델마다 개발용 전체의 답을 한 번씩 받아 보관하고(이때 모델의 글당 평균 판정 시간을 잰다), 조합(보낼 글 두 방식 × 확신 '낮음' 처리 두 가지)별 SC-001~SC-007을 보관한 답으로 계산한다. 조합의 시간은 '90일 창에서 그 방식이 LLM에 보내는 글 수 × 그 모델의 글당 평균'이다(2026-11-09 사용자 결정).
- **FR-021**: SC-001~SC-007을 모두 넘기는 조합 중 시간이 가장 짧은 조합을 고른다. 시간이 같으면 SC-001(기회 여부), 그다음 SC-003(종류)이 높은 조합을 고른다. 모두 넘기는 조합이 없으면 가장 많이 넘기는 조합을 고르고(같으면 같은 순서) 사용자에게 알린다.
- **FR-022**: 최종 평가용은 2025-01-01~04-30 게시글 중 스펙 1과 같은 방법(글 식별자 SHA-1 순서)으로 고른 100건이다. 스펙 1 FR-032와 같은 교차 라벨로 확정하고, 측정 전까지 누구도 이 100건에 규칙이나 LLM을 돌리지 않는다. 고른 조합으로 한 번만 잰다.
- **FR-023**: 정답셋 비교는 실행과 같은 판정 경로(규칙, LLM, 보관한 답)를 써야 한다. 다만 서버에 닿지 못한 글(K)이 하나라도 있으면 점수를 내지 않고 종료 코드 1로 끝낸다(스펙 1의 '본문 못 받음'과 같다). 글 판정 실패(C)는 실행처럼 규칙 결과로 점수에 넣고, 실패 수를 점수와 함께 보인다(2026-11-09 사용자 결정).
- **FR-024**: 고른 방식이 기준 문서와 다르면 `docs/product/decisions.md`에 넣을 결정 로그 초안을 사용자에게 낸다.

**검사와 보호**

- **FR-025**: LLM 입력 자르기, 답 읽기와 검사, 보관, 보낼 글 고르기, 확신 '낮음' 처리, 연결 실패 처리, 요약 줄은 LLM 서버 없이 도는 자동 검사로 확인되고, 저장소의 기존 자동 검사에 들어가야 한다.
- **FR-026**: 판정용 LLM은 이 컴퓨터에서 돌아야 한다. 공지 본문을 외부 서비스로 보내지 않는다(정답셋 교차 라벨은 스펙 1과 같은 방법이라 예외).

### 스펙 1과의 관계

- 스펙 1 FR-024(요약 줄)와 FR-011(근거 값)이 FR-016·FR-017대로 바뀐다. 나머지 스펙 1 요구는 그대로다.
- 스펙 1 정답 기준을 그대로 쓴다. 새 기준이 필요하면 스펙 1 spec '정답 기준'에 더한다.

### Key Entities *(include if feature involves data)*

- **LLM 판정**: 글 하나에 대한 LLM 답. 기회 여부, 종류, 주최, 확신, 모델 이름, 지시문 판을 가진다.
- **판정 방식**: 보낼 글(확인 필요만 / 모든 글)과 확신 '낮음' 처리(받기 / 확인 필요)의 조합.
- **후보 모델**: 비교할 로컬 모델. 이름, 크기, 개발용 지표, 글당 판정 시간을 가진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

판정은 최종 평가용(2025년 1~4월 100건)에서 한다. 지표의 정의와 분모는 스펙 1과 같다.

- **SC-001**: 규칙과 LLM이 확인 필요로 보내지 않은 글 중 기회 여부가 정답과 맞는 비율이 95% 이상이다.
- **SC-002**: 정답이 기회인 글 중 기회 아님으로 뺀 비율이 3% 이하다.
- **SC-003**: 결과와 정답이 모두 기회로 본 글 중 종류가 맞는 비율이 90% 이상이다.
- **SC-004**: 결과와 정답이 모두 기회로 본 글 중 마감을 채운 글에서 마감이 정답과 같은 비율이 95% 이상이다.
- **SC-005**: 결과와 정답이 모두 기회로 보고 정답 마감이 날짜인 글 중 마감을 채운 비율이 70% 이상이다.
- **SC-006**: 결과와 정답이 모두 기회로 본 글 중 주최를 채운 글에서 주최가 정답과 같은 비율이 90% 이상이다.
- **SC-007**: 확인 필요로 남은 글이 전체의 10% 이하다.
- **SC-008**: 하루치 새 글(10건 이하)의 실행이 LLM 판정까지 3분 안에 끝난다. 90일치 첫 실행은 '모든 글' 방식이어도 40분 안에 끝난다.
- **SC-009**: LLM 서버가 꺼져 있을 때 실행 시간이, 서버를 켜고 보낼 글의 답이 모두 보관된 상태에서 같은 명령을 돌린 실행보다 10초 넘게 늘지 않는다.
- **SC-010**: 같은 입력으로 다시 실행하면 결과 파일의 판정과 근거가 모두 같다(수집 시각만 다르다).

## Assumptions

- 실행 컴퓨터는 Apple M5 Pro, 메모리 24GB이고 Ollama가 설치돼 있으며 Gemma 4 E4B를 받아 두었다(2026-11-09 확인). 14B급까지는 넉넉하고 27~32B급은 빠듯하다.
- 다른 팀원 컴퓨터에는 LLM 서버가 없을 수 있다. 그때는 US3대로 규칙 결과로 돈다.
- 판정 LLM은 이 컴퓨터에서만 돌아서 공지 본문이 밖으로 나가지 않는다. 정답셋 교차 라벨은 스펙 1처럼 Claude·codex 라벨러를 쓴다.
- 마감 규칙은 스펙 1 그대로 쓴다. LLM은 마감을 뽑지 않는다.
- 같은 브랜치에서 로컬로 작업하고 커밋과 올리는 때는 사용자가 정한다. 원문과 키는 커밋하지 않는다.
- 범위 밖: LLM으로 마감 뽑기, 외부 API 모델, 관리자 화면, 다른 출처 게시판.

## 후속 작업

- 관리자가 판정 모델을 골라 교체하는 화면과 관리자 모니터링 대시보드(2026-11-09 사용자 요청). 지금은 관리자 화면이 없다. FR-011의 설정 한 곳이 그 화면이 바꿀 자리다.
